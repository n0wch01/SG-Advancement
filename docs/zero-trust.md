## PDP와 PEP

PDP(정책 결정 지점)는 다음 두 가지다.

- 관제 서버의 서명된 정책(공통 기준선과 팀별 강화)
- 엔드포인트의 로컬 판정 엔진(같은 룰)

PEP(정책 시행 지점)는 판정을 집행만 한다. PEP는 상태를 라벨로 붙이고(`labels.sga_*`), 판단은 서명된 룰이 한다.

| 안내서 PEP | SG-Advance | 수준 |
|---|---|---|
| 내부 PEP (도구 호출 의도 검증) | Claude Code hook, OpenClaw 플러그인, MCP 게이트웨이 `tools/call` | 실행 전 차단·승인 |
| 외부경계 PEP | egress 프록시(허용 목록), **중앙 MCP 게이트웨이**(사내 MCP 서버로 가는 유일한 길, 자격증명 보관; 아래) | 차단 |
| 입력 PEP | MCP 게이트웨이와 **Claude Code PostToolUse hook**: 인젝션 high 이상인 결과는 모델에 넘기지 않음(`updatedToolOutput`). OpenClaw 플러그인은 탐지만 함 | 차단 |
| 위임 PEP | OpenClaw 위임 사슬, **Claude Code 하위 에이전트**(hook의 `agent_id`로 위임 트리 구성): 위임 전파(T18)와 인젝션 문구를 하위 에이전트에 넘기는 것을 차단 | 차단 |
| 피지컬 PEP | — | 범위 밖 |

"차단"이 실제로 일어났는지는 따로 기록한다([fail-closed.md](fail-closed.md#2-결과-기록-모델-enforcement)).

- **확인됨**: 길목에 있는 PEP가 직접 막은 경우다. MCP 게이트웨이와 egress 프록시가 여기에 든다.
- **미확인**: 판정을 에이전트에게 넘긴 경우다. Claude Code hook과 OpenClaw 플러그인이 여기에 든다.
- 장애와 판정 실패의 처리도 같은 문서에 있다.

## 유일한 길: 중앙 MCP 게이트웨이와 자격증명 보관 (2026-11-13)

제로트러스트에서 PEP가 의미 있는 이유는 그것을 거치지 않고는 리소스에 닿을 수 없기 때문이다.
그래서 사내 MCP 서버(예: CRM)는 다음 구조로 둔다(compose 프로필 `mcp`).

```
Claude Code ─▶ 노트북 센서의 로컬 게이트웨이 ─▶ LAN 게이트웨이 nginx ─▶ 중앙 MCP 게이트웨이 ─▶ 사내 CRM
              (PC 상태·사람 위험도·작업 범위 판정)   (장비 인증서 mTLS,       (서명된 정책으로 판정,     (crm-net: 내부망,
                                                  요청마다 관제 서버에        CRM 토큰을 여기서만 붙임,   토큰 없으면 401)
                                                  폐기 여부 확인)            nginx 비밀값 없으면 403)
```

- **에이전트에는 자격증명이 없다**: CRM 토큰은 중앙 게이트웨이만 가진다(`--mcp-credential crm=ENV`). 에이전트가 보낸 `Authorization`·`Cookie`는 버린다.
- **우회할 길이 없다**: CRM은 중앙 게이트웨이와만 같은 내부망(`crm-net`)에 있다. 중앙 게이트웨이는 LAN 게이트웨이가 붙이는 비밀값이 없으면 거부한다.
- **지속 검증**: nginx는 `/mcp/` 요청마다 관제 서버(`/v1/gateway/authz`)에 장비 인증서의 주인이 등록·미폐기·미만료인지 묻는다. 폐기하면 다음 요청부터 끊긴다.
- **두 겹의 판정**: 노트북(그 PC의 상태와 사람)과 중앙(회사 공통 정책). 중앙 기록에는 사람(`X-SGA-User`, 장비 센서가 알림)과 장비(nginx가 인증서로 확인)가 함께 남는다.
- 한계: 사람의 신원은 장비가 말한 값이다(장비 인증서로 장비만 증명). 사람 단위 인증(SSO)은 범위 밖.

실환경 확인(2026-11-13, 노트북 역할의 시험 장비를 LAN 경로로 등록, 임시 HOME):

| 시도 | 결과 |
|---|---|
| 에이전트 → 로컬 게이트웨이 → LAN(mTLS) → 중앙(토큰) → CRM. 에이전트는 가짜 토큰을 붙임 | **성공**(가짜 토큰은 버려짐). 노트북·중앙 양쪽에 기록 |
| 장비 인증서 없이 LAN 게이트웨이로 | **403** |
| 사내망의 다른 PC(carol-pc)에서 중앙 게이트웨이로 직접, 장비 헤더 위조 | **403**(비밀값 없음) |
| 사내망의 다른 PC에서 CRM으로 직접 | **연결 불가**(crm-net에 없음) |
| CRM에 토큰 없이 | **401** |
| 보안팀이 장비 폐기 → 같은 호출 | **403**, 에이전트에는 "회사 MCP 게이트웨이가 이 장비를 거부" MCP 오류로 전달 |

시험 장비 `zt-laptop-test`는 폐기했다.

## 작업 범위 프로필 (의도 검증에 대한 입장)

안내서 시나리오 1은 "문서 분석 중 메일 발송"처럼 작업 목적과 행위의 불일치를 잡는다.
결정(2026-11-13): **LLM으로 의도를 판정하지 않는다**(안내서 각주 8: 판정기 자체가 인젝션 대상). 대신 두 가지를 쓴다.

1. **행동 기반**: 인젝션을 읽은 뒤의 민감 행동(같은 세션·위임 트리), 등급별 승인.
2. **작업 범위 프로필**(`task-scope-outside-profile`, 안내서 P5-7): 공통 정책에서는 꺼져 있다. 팀 정책이 켜고 허용 툴을 그 팀 업무로 좁힌다
   (팀은 더 엄격하게만 바꿀 수 있음). 범위 밖 툴은 사람이 확인한다.
   예: CRM 분석팀 → `Read, Grep, Glob, LS, mcp__crm__query_customers`. 같은 장비라도 팀에 넣어야 적용된다(시험 `test_a_team_turns_on_its_task_scope_profile`).

## 가역성·실시간성 등급 (안내서 표 2-5)

행동(`tool.call`)을 판정하는 룰에는 `grade:<등급>` 태그를 단다. 상태나 사람을 기준으로 판단하는 룰은 `action-independent`로 표시한다.

- 결정(2026-11-13): 응답은 사용자가 정한다. 등급과 응답이 어긋나면 시험이 알려 주고, 자동으로 바꾸지 않는다(`tests/test_rule_cases.py`).
- 2-1과 3-1 등급은 사람의 명시적 승인 이상이어야 한다.
- 3-1 등급을 사람이 승인하는 경우 사후 감사가 붙어야 한다. 그래서 severity는 high 이상이어야 하고, `user-approved-high-risk`가 감사한다.

### 승인 원칙 (2026-11-14)

결정: 사용자 승인을 먼저 받고, 매우 위험한 것만 바로 차단하며, 보안팀은 사후에 확인한다.

| 구분 | 무엇 | 처리 |
|---|---|---|
| 바로 차단 | 공격 진행 신호(인젝션 뒤 민감 행동, 인젝션 문구를 하위 에이전트에 넘김, 위임 전파), 외부 유출(보호 데이터·비밀값·민감 파일의 외부 전송, 미허가 외부 호스트) | 사용자 승인 없이 차단 |
| 사용자 승인 | 그 밖의 위험 행동: 되돌릴 수 없는 삭제(파괴적 셸·SQL·클라우드 명령), 목적지가 안 보이는 보호 데이터 전송 등. 3-1 등급 포함 | 에이전트 확인 창. MCP 게이트웨이는 사람에게 물을 수 없어 보안팀 보류 |
| 보안팀 사후 검토 | 사용자가 승인한 high·critical 호출 | 콘솔 승인 감사의 "보안팀 검토 대기"에서 확인함·문제 있음으로 표시한다(감사 체인에 기록). 문제가 있으면 Finding 화면에서 사람·대화 차단 |
| 그대로 둠 | 실패 처리(정책 만료, PC 상태 미달, 출처 기록 손상, 데몬·판정 실패), 보안팀이 이미 내린 결정(원격 차단, 변조·미승인 플러그인·스킬·MCP 격리), 위험도가 높아진 사람의 민감 리소스 접근(보안팀 승인), 폭주 중단 | 사용자 승인으로 넘기지 않음 |

- 마지막 줄은 사용자 승인으로 내리면 차단된 사람이 스스로 풀 수 있게 된다. CLAUDE.md의 "장애를 사용자 승인만으로 넘기지 않는다"와도 맞지 않는다.
- 실행 전에 보안팀이 봐야 하는 룰은 팀 정책에서 응답을 `security_approval`로 올리거나 `approval:security` 태그를 붙인다.

| 등급 | 룰 |
|---|---|
| 0 (조회) | `sensitive-file-access` |
| 2-1 (에이전트 간 전달) | `cross-agent-injection-propagation`, `injection-relayed-to-agent`, `delegation-grants-more-permission`(사용자 승인) |
| 3-1 (영구 삭제·외부 유출) | 사용자 승인: `destructive-shell-command`, `destructive-sql`, `destructive-cloud-command`, `destructive-after-external-input`, `run-downloaded-file`, `pipe-download-to-shell`, `protected-data-destination-unclear`. 차단: `sensitive-file-exfil-command`, `secret-in-tool-arguments`, `injection-then-sensitive-action`, `injection-then-destructive-action`, `protected-data-to-unapproved-destination`, `transfer-with-lineage-unavailable` |

2-2와 3-2 등급(실시간이라 사전 승인 정책 안에서 자동 실행)은 해당하는 행동이 없어 쓰지 않는다.

## 접근 결정 ([rules/zero_trust.yaml](../rules/zero_trust.yaml))

| 룰 | 근거 | 조건 | 응답 |
|---|---|---|---|
| `policy-stale-state-changing-tool` | 안내서 2장 4절 3): 캐시 정책 유효기간 | 관제 서버가 정책을 72시간(`SGA_POLICY_MAX_AGE_HOURS`) 확인해 주지 못함 + 읽기 전용이 아닌 툴 | 사람 확인 |
| `sensitive-resource-from-degraded-device` | P2-1·P2-2: 상태 미달 기기의 민감 데이터 접근 제한 | PC 상태 `degraded`(hook 없는 Claude Code, 통제 밖 에이전트) + 민감 리소스 | 차단 |
| `sensitive-resource-by-elevated-risk-user` | P1-4·C1-7: 위험도 지속 재평가 | 관제 서버가 고위험으로 내려보낸 사람 + 민감 리소스 | 보안팀 승인 |

- **민감 리소스**는 정책이 정한다. 지금은 MCP 서버 `crm`, `hr-db`, `payments`(예시)이고, 두 룰이 같은 목록을 쓴다.
- **PC 상태**는 센서 점검으로 정해진다. Claude Code hook 위치 점검과 설치 탐지 결과를 합친다.
  - 라벨: `sga_posture`(ok / degraded / unknown)와 `sga_posture_reasons`
  - 상태가 고쳐지면 다음 점검에서 자동으로 풀린다.
- **사람의 위험도**([server/risk.py](../src/sg_advance/server/risk.py)):
  - 최근 24시간 동안 critical 1건 이상, 또는 high 3건 이상이면 고위험이다.
  - **에이전트의 행동에서 나온 Finding만** 센다: 툴 호출·결과, 프롬프트, 응답, 승인.
  - 설치·설정·인벤토리·무결성처럼 PC 설정에서 나온 Finding은 세지 않는다. 그쪽은 PC 상태 룰이 처리한다.
  - 각 PC는 **그 PC를 쓴 사람의 위험도만** 받는다. 고위험자 명단 전체를 뿌리지 않는다.
- 위험도 반영 경로: 센서는 flush 주기마다 `GET /v1/risk`를 호출하고, 결과를 `elevated_risk_users` 집합에 넣는다. 관제 서버와 연결이 끊겨도 위험도를 낮추지 않는다.
- 알려진 공백:
  - 상태가 `unknown`이면 막지 않는다. 점검을 끈 센서이거나, 시작 직후 첫 점검 전인 경우다.
  - 위험도 기준값(1/3건, 24시간)은 코드 상수다.
  - 인젝션된 페이지를 읽은 것(tool.result)도 행동으로 센다. 피해자도 위험도가 올라간다.

## 감사 로그 변조 방지 (안내서 C1-6, 금융보안원 ⑰)

[server/audit_chain.py](../src/sg_advance/server/audit_chain.py)가 다음 기록을 순서대로 해시 체인에 묶는다.

- 대상: Finding, 원격 대응과 그 결과, 보안팀 승인 결정, 정책 변경
- 연결식: `hash = sha256(prev | seq | kind | ref_id | digest | ts)`
- 검증 명령: `sga-server audit chain`
  - 기록을 바꾸거나, 지우거나, 순서를 바꾸면 그 지점부터 깨진다.
  - 끝부분을 잘라 내면 짧지만 유효한 체인이 남는다. 그래서 체인 머리(`GET /v1/admin/audit/chain`)를 밖에 보관해 두고 `--expect-head`로 비교한다.

## 승인 피로 지표 (안내서 C2, 금융보안원 ⑭)

`GET /v1/admin/approvals/metrics?days=7`의 결과를 대시보드 승인 감사 화면 위쪽에 보여 준다.

- 사용자 승인과 보안팀 승인을 나눠서 다음을 계산한다.
  - 요청 수와 반려율
  - 승인 소요 시간(중앙값, 상위 10%)
  - 5초 안에 승인한 비율
- 같은 룰과 툴로 5번 이상 요청됐고 95% 이상 승인된 유형은 **자동화·룰 조정 후보**로 표시한다. 조정 여부는 사용자가 정한다.
