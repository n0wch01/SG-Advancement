# 장애·판정 실패 처리표와 결과 기록 (1차 작업, 2026-11-13)

CLAUDE.md 원칙:

- **유효한 정책이나 필수 승인 근거를 확인할 수 없는 실행은 보류·차단한다.** 장애를 사용자 승인만으로 넘기지 않는다.
- 탐지, 승인 요청, 실행 보류, 단일 호출 차단, 세션 중단, 실제 적용 확인을 구분해 기록한다.

결정(2026-11-13):

- 장애나 낡은 정책에서는 읽기 전용 툴만 허용하고 나머지는 차단한다.
- MCP 게이트웨이의 승인 요청은 보안팀 보류 경로로 보낸다.
- 2026-11-14 변경: 3-1 등급도 사용자가 먼저 승인하고, 보안팀이 사후 검토 큐에서 확인한다([zero-trust.md](zero-trust.md#승인-원칙-2026-11-14)). 전에는 3-1을 보안팀 보류로 보냈다.

## 1. 장애·판정 실패 처리표

| 상황 | Claude Code hook | OpenClaw 플러그인 | MCP 게이트웨이 |
|---|---|---|---|
| 데몬 없음 | 서명된 캐시 정책으로 판정(`degraded`). 보안팀 승인이 필요하면 **차단**(기다릴 데몬이 없음) | 같음(`sga-sensor evaluate`) | 데몬 안에서 돌아감. 데몬이 죽으면 게이트웨이도 없어 **연결 불가** |
| 데몬도 없고 캐시 정책도 없음·변조됨 | 읽기 전용 툴만 통과, 나머지 **차단**(전에는 사용자에게 물음) | 같음(전에는 사용자에게 물음) | 해당 없음 |
| 정책이 72시간 넘게 확인되지 않음 | `policy-stale-state-changing-tool`: 읽기 전용이 아닌 툴 **차단**(전에는 사용자 확인) | 같음 | 같음 |
| PC 상태를 모름(점검하는 PC인데 결과가 없거나 1시간 넘게 낡음) | 민감 리소스 **차단**(`sensitive-resource-from-degraded-device`, 전에는 통과) | 같음 | 같음. 중앙 게이트웨이처럼 PC 상태를 점검하지 않는 센서는 라벨을 붙이지 않음 |
| hook 입력이 JSON이 아님, hook 내부 오류 | exit 2로 **차단**(전에는 Claude Code의 onFailure에 맡김) | 해당 없음 | 처리 중 오류는 502(전달 안 함) |
| hook 프로세스가 없음·실행 실패·시간 초과 | PreToolUse와 PostToolUse 모두 `onFailure: block`(전에는 PreToolUse만) | 플러그인이 꺼지면 `openclaw-plugin-heartbeat-lost`와 `openclaw-guard-plugin-disabled`로 탐지 | 해당 없음 |
| 보안팀 승인 대기 중 관제 서버에 연결 불가 | **거부**(`unreachable`) | 같음 | 같음 |
| 보안팀이 5분 안에 결정 안 함 | **거부**(`timeout`) | 같음 | 같음 |
| 승인 결정이 다른 요청을 가리킴(다이제스트 불일치·없음) | **거부**(`mismatch`) | 같음 | 같음 |
| 승인 후 실행 직전 다시 판정해 차단 조건이 생김(원격 차단, PC 상태, 위험도, 정책 만료, 작업 범위) | **거부**(`rechecked`) | 같음 | 같음 |
| 승인 요청(require_approval) 판정 | Claude Code 확인 창(3-1 포함, 2026-11-14). `approval:security` 태그가 붙은 룰만 보안팀 보류 | OpenClaw 확인 창(같음) | **항상 보안팀 보류**(사람에게 물을 수 없음). 보류할 수 없으면 차단. "허용"이 아닌 판정은 모두 거부 |
| 툴 결과가 1MB를 넘음 | `tool-result-uninspected`로 결과 가림 | 탐지만 함(가릴 수 없음) | 결과 가림 |
| 툴 결과를 읽을 수 없음(JSON-RPC가 아님, SSE 데이터가 깨짐) | 해당 없음 | 해당 없음 | 결과 가림(전에는 그대로 통과) |
| 데이터 출처 기록(`lineage.json`)을 읽을 수 없음 | 미승인 목적지로 가는 호출 **차단**(`transfer-with-lineage-unavailable`), 로컬·사내는 통과 | 같음 | 같음 |
| 원격 조치 결과 보고가 유실됨 | 60초 임대가 끝나면 다시 전달(최대 5번). 센서는 같은 조치를 다시 실행하지 않고 저장한 결과만 보고. 끝내 응답이 없으면 `unacknowledged`로 실패 | 같음 | 같음 |

툴 결과 검사는 hook과 게이트웨이 모두 결과 **전체**(최대 1MB)로 한다. 기록에는 앞 4000자만 남긴다(전에는 앞 4000자만 검사).

## 2. 결과 기록 모델 (`Enforcement`)

| 칸 | 값 | 뜻 |
|---|---|---|
| `stage` | detected / approval_requested / held / blocked / result_withheld / session_aborted / quarantined | 무엇을 하기로 했나. 값이 없으면 `action`으로 정함 |
| `confirmation` | not_applicable / unconfirmed / confirmed / contradicted / failed | 부작용이 실제로 일어나지 않았다고 확인됐나 |
| `evidence` | 문장 | 어떻게 확인했는지, 또는 왜 확인하지 못하는지 |

**확인됨(confirmed)**은 집행 지점이 직접 부작용을 막은 경우에만 쓴다.

- MCP 게이트웨이 거부: 업스트림으로 보내지 않았다.
- 게이트웨이 결과 가림: 에이전트로 보내는 바이트를 게이트웨이가 바꿨다.
- 게이트웨이 툴 격리: tools/list에서 뺐다.
- egress 프록시 거부: 연결을 열지 않았다.

**미확인(unconfirmed)**은 판정을 에이전트에게 넘긴 경우다. Claude Code hook과 OpenClaw 플러그인의 차단, hook의 결과 가림이 여기에 든다. 에이전트가 따랐는지는 직접 알 수 없다.

**반증(contradicted)**: 차단했던 호출의 결과가 나중에 들어오면 `enforcement-contradicted`(critical)를 기록한다. 원래 차단 기록은 고치지 않는다(해시 체인). 새 기록이 원래 Finding을 가리킨다(`sga_contradicted_findings`).

관제 화면에는 "차단 · 실제 적용 확인", "차단 · 적용 미확인", "결과 가림 · 적용 미확인"처럼 단계와 확인 상태가 함께 보인다.

## 3. 원격 조치: 요청과 실제 적용 구분

`applied` 값:

- `applied`: 바뀜
- `already_applied`: 이미 그 상태
- `not_supported`: 이 장비에 그 집행 지점이 없음
- `failed`: 실패
- `unacknowledged`: 5번 전달해도 응답 없음

중복 보고는 무시하고 처음 보고를 유지한다.

## 3-1. 반복 집행도 매번 기록 (2026-11-13 결정)

실환경 확인 4번에서 같은 대화의 두 번째 보류가 Finding 없이 보안 승인 기록에만 남았다. 원인은 룰의 `dedup: session`이다.

- 이제 집행 지점이 실제로 막거나 보류한 호출은 반복이어도 매번 Finding이 된다(`labels.sga_repeat=true`).
- 보류 기록의 `finding_ids`도 이 Finding을 가리킨다.
- 경보만 내는 룰, 에이전트 확인 창, 감시 모드의 반복은 그대로 한 건이다.
- 영향: 같은 사람이 막힌 시도를 반복하면 사람 위험도 점수에 그만큼 더해진다(의도: 반복 시도는 신호다).

## 4. 실환경 확인 (2026-11-13)

환경:

- 실제 관제 서버(마이그레이션 0008)에 시험 장비 `p1-mac-test`를 등록했다.
- 센서 안의 MCP 게이트웨이를 가짜 사내 MCP 서버 앞에 두었다.
- 성공 여부는 로그가 아니라 **가짜 서버가 실제로 요청을 받았는지**로 판단했다.

| # | 한 것 | 결과 |
|---|---|---|
| 1 | `query_customers`에 `DELETE FROM users`를 넣어 호출 | 보안팀 보류. 승인 전에는 가짜 서버에 요청이 오지 않음. Finding은 `held · confirmed` |
| 2 | 보안팀이 승인 | 업스트림으로 1번 전달, 응답이 에이전트에게 감. 승인 기록의 결과는 `allowed`, 다이제스트가 저장됨 |
| 3 | `DROP TABLE customers`로 다시 호출, 대기 중 원격 조치로 그 사람을 차단 | 원격 조치는 `done`, 전달 1번, `applied` |
| 4 | 그 뒤 보안팀이 승인 | 실행 직전 재검사에서 거부("보안팀이 차단한 사람"). 승인 기록의 결과는 `rechecked`, 가짜 서버는 요청을 받지 않음 |

끝난 뒤 사람 차단은 장비와 함께 정리했다(시험 장비 폐기).

## 5. 한계 (막을 수 없거나 확인할 수 없는 것)

- **Claude Code·OpenClaw 확인 창으로 간 승인**: 사람이 누르는 순간 에이전트가 바로 실행한다. 승인 후 재검사와 요청 동일성 확인을 할 수 없다.
  - 2026-11-14 결정으로 3-1도 여기로 간다. 대신 보안팀이 승인된 high·critical 호출을 사후 검토 큐에서 하나씩 확인한다.
  - 실행 전에 보안팀이 봐야 하는 룰은 `approval:security` 태그를 붙이면 보안팀 보류(재검사·요청 동일성 확인)로 간다. 기본 정책에는 붙은 룰이 없다.
  - 사용자가 거절하면 Claude Code는 결과를 남기지 않아, 거절과 포기를 구별하지 못한다.
- **hook의 결과 가림**: Claude Code가 `updatedToolOutput`을 적용했는지 hook은 알 수 없다. 내장 툴은 출력 형식이 다르면 원본을 쓴다. 그래서 확인됨이 아니라 미확인으로 기록한다. 차단 사유는 함께 전달된다.
- **PostToolUse의 `onFailure: block`**: Claude Code가 이 이벤트에서 어떻게 처리하는지는 실제 Claude Code로 확인해야 한다(노트북 실설치).
- **반증 감지의 범위**: 에이전트가 차단을 무시했더라도 결과 이벤트가 오지 않으면 모른다. 센서를 다시 시작하기 전의 차단은 기억하지 못한다(24시간, 최대 5000건).
- **재검사의 범위**: 승인 후 재검사는 기록을 남기지 않는 새 엔진으로 한다. 시퀀스 룰(앞뒤 행동의 연결)은 보류할 때 이미 판정했으므로 재검사에서는 빈 상태로 시작한다.
- **관리자 권한 없이 설치한 PC**: 사용자가 센서 파일(정책 캐시, 상태 결과)을 지우거나 데몬을 끌 수 있다. 이 경우에도 결과는 차단 쪽(읽기 전용만 허용)이다. hook 자체를 지우는 것은 사용자 설정 설치에서 막을 수 없고 탐지만 한다(`claude-code-guard-hook-removable`).
- **정책 나이**: PC의 시계를 기준으로 계산한다. 시계를 되돌리면 낡은 정책을 새것으로 보이게 할 수 있다.
