# 평가 (1주 계획 5번, 2026-11-14)

두 가지를 했다.

1. **같은 공격을 세 집행 지점에 넣은 표**: 각 지점의 실제 판정 코드에 공격·우회 시도·정상 작업 묶음을 넣었다(`scripts/evaluate.py`, `eval/corpus.yaml`).
2. **운영 기록 다시 돌리기**: 운영 관제 서버에 쌓인 실제 이벤트를 지금 룰로 다시 돌렸다(물량·오탐 후보).

결과 표 전체는 [evaluation-results.md](evaluation-results.md)에 있다(스크립트가 만든 파일). 테스트(`tests/test_evaluation.py`)가 설계와 어긋나는 결과를 회귀로 잡는다.

## 1. 세 집행 지점 비교

### 방법

| 지점 | 무엇에 넣었나 | 막았는지 판단 |
|---|---|---|
| Claude Code hook | 데몬이 hook 요청을 판정하는 함수(`judge_event`), PreToolUse·PostToolUse 입력 그대로 | hook의 결정(deny / ask / 결과 가림) |
| OpenClaw 플러그인 | 플러그인 요청 판정 함수(`judge`). 툴 결과는 게이트웨이 WebSocket 관측 경로 | 플러그인 결정(block / requireApproval) |
| MCP 게이트웨이 | 실제 게이트웨이를 가짜 사내 MCP 서버 앞에 띄움 | **서버가 요청을 받지 않았는지**까지 확인 |

- 판정에는 저장소의 룰을 그대로 쓴다. 관제 서버는 프로세스 안에서 띄운다.
- 사람 확인(approve)은 승인 원칙(2026-11-14)에 따라 "멈춤"으로 센다. 사용자가 승인해야 실행되고, 승인하면 보안팀 사후 검토로 간다.

### 결과 요약

2026-11-14 위협 인텔리전스 목록을 넣으며 공격 2종(A16 악성 MCP 패키지 실행, A17 메일 숨은 참조로 악성 도메인 전송)을 더했다. 아래 수치는 더한 뒤의 것이다.

| | Claude Code hook | OpenClaw 플러그인 | MCP 게이트웨이 |
|---|---|---|---|
| 공격 17종: 설계대로 처리 | 16/16 | 12/12 | 6/6 |
| 공격 + 우회 시도에서 멈춘 비율 | 74% (23건 중 막음 10, 확인 7) | 67% (18건 중 막음 6, 확인 6) | 100% (6건 중 막음 6) |
| 정상 작업 오탐 | 0/40 | 0/38 | 0/2 |
| 판정 지연 중앙값 / 95% | 0.9 / 1.4 ms | 0.9 / 1.1 ms | 2.1 / 2.5 ms(서버 왕복 포함) |

### 어떻게 읽어야 하나

- **공격 묶음은 룰을 만든 사람이 짰다.** 그래서 "설계대로 34/34"는 탐지 성능이 아니라 **설계대로 구현됐다는 확인**이다.
- 이 한계를 줄이려고 **우회 시도 7종**을 함께 넣었다. 각 문서에 적은 한계를 실제로 시험한 것이고, 7종 모두 문서가 예측한 대로 통과했다.
  - 경로를 숨긴 `.env` 전송
  - 스크립트 안에서 하는 삭제
  - 문구를 바꾼 인젝션
  - base64로 바꾼 보호 데이터
  - 변수로 만든 실행 경로
  - 문구를 바꾼 위임 지시
  - `find -delete`
  
  "멈춘 비율"은 이 우회 시도를 포함해 계산했다.
- **지점별 차이**:
  - OpenClaw가 낮은 이유: 툴 결과를 가릴 수 없고(탐지만), MCP 툴 경로가 없다.
  - MCP 게이트웨이가 100%인 이유: 게이트웨이를 지나는 호출만 보기 때문이다. 셸 명령은 보지 못한다(해당 없음 "–").
  - 세 지점이 서로 다른 것을 보므로 **함께 써야 한다**.
- **정상 작업 오탐 0%도 같은 한계가 있다**: 직접 고른 40종이다. 실제 사용 기록 결과는 아래 2절에 있다.
- **우회는 패턴 기반 판정의 본질적 한계다**: 값·문구를 바꾸면 놓친다. 그래도 MCP 게이트웨이와 보안팀 사후 검토가 남는다. 보완 방향(출처 기반 오염 추적, ML 분류기)은 미룬 과제에 있다.

## 2. 운영 기록 다시 돌리기 (물량·오탐 후보)

운영 관제 서버의 이벤트를 지금 룰로 다시 돌렸다(`sga-detect`). 복사본은 이 PC 안에서만 다뤘다.

- 기간: 2026-11-11 ~ 11-14
- 이벤트 3,489건. 외부 통신 1,503, 인벤토리 1,262, 툴 호출 158, 툴 결과 108 등이다. 대부분은 데모·시험에서 나왔다.
- Finding 125건. 대부분 설정·상태 경보다.
  - `openclaw-sandbox-off` 26
  - `ai-agent-outside-control` 20
  - `openclaw-gateway-network-exposed` 12
  - 기타

### 직접 확인한 행동 판정 (시험 장비 제외)

두 오탐은 룰 케이스를 먼저 넣고 고쳤다. 고친 룰로 운영 기록을 다시 돌리니 두 건 모두 사라졌다. 남은 `destructive-shell-command` 1건은 시험 장비에서 실제로 실행한 `rm -rf`다.


| 룰 | 무엇 | 판단 |
|---|---|---|
| `identical-args-loop` (세션 중단) | 팀 게이트웨이 에이전트가 `get_goal`(목표 조회, 무해)을 같은 인자로 반복 | **오탐 → 수정**(사용자 결정 2026-11-14): 상태만 읽는 툴(`get_goal`, `session_status` 등)을 룰에서 뺐다. 이 툴들로 도는 루프는 `rate-limit-tool-calls`만 본다 |
| `destructive-shell-command` (사용자 승인) | OpenClaw Code Mode의 바깥 호출(JavaScript 안에 명령이 들어 있음) | **오탐 → 수정**(사용자 결정 2026-11-14): 같은 승인 룰(`destructive-sql`·`destructive-cloud-command`)처럼 바깥 호출을 건너뛴다. 안쪽 실제 명령에서 한 번만 묻는다 |
| `sensitive-resource-from-degraded-device` (차단) | 중앙 MCP 게이트웨이가 PC 상태 `unknown`으로 `query_customers`를 막음(11-13 08:34) | **이미 고쳐짐**. 1차 작업 수정 전의 기록이다. 지금 중앙 게이트웨이는 PC 상태를 점검하지 않는 센서로 돌아 라벨을 붙이지 않는다(`--no-discovery --no-claude-code`) |
| `egress-unapproved-host` (차단) | `telemetry.openclaw.ai`, `wttr.in`, `www.gravatar.com`, `example.com` | 정책대로다(허용 목록 결정 2026-11-12) |
| `user-approved-high-risk` (경보) | 데모에서 사람이 승인한 exec | 정상(사후 감사 대상) |

**물량 문제**: 인벤토리·설정 스냅샷이 주기적으로 와서 같은 경보가 반복된다(`openclaw-sandbox-off` 26건 등). 기기·하루 단위로 묶는 것을 검토할 수 있다.
