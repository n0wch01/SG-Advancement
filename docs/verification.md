# 검증 구조 (2026-11-17)

에이전트의 행동 하나가 어떤 순서로, 무엇에 의해 검사되는지 정리한다. 처음에는 기능을 하나씩 붙였다. 그래서 "어디서 무엇을 믿고 판정하는가"가 문서마다 흩어져 있었다. 이 문서는 그것을 다섯 단으로 다시 묶는다. 새로 만든 것은 2b(승인-실행 대조), 2a의 실행 방식(분류기 별도 프로세스), 4의 검증 스크립트다. 나머지는 이미 있던 것에 자리를 정해 준 것이다.

## 원칙

1. **실행 전에는 결정적인 검사만 한다.** 같은 입력이면 같은 판정이 나오고, 왜 그런지 룰 하나로 설명되고, 걸리는 시간에 상한이 있다. 분류기·LLM 같은 확률적 판단은 실행 전 경로에 넣지 않는다.
2. **뒤 단계는 올리기만 한다.** 분류기나 사후 탐지는 경보를 내고, 결과를 가리고, 이후 실행을 막을 수 있다. 앞 단계가 막은 것을 풀지는 못한다(분류기가 `benign`이라고 해도 룰이 가린 결과는 가려진 채로 둔다).
3. **막을 수 없는 자리는 탐지로 메우고, 메웠다는 사실을 기록한다.** 막지 못한 것을 막았다고 기록하지 않는다. "탐지", "승인 요청", "보류", "단일 호출 차단", "대화 중단", "실제 적용 확인"은 따로 남긴다.
4. **정책 변경도 검증 대상이다.** 룰을 고치는 일이 통제를 약하게 만들 수 있다. 약해지는 변경은 사람이 읽기 전에는 나가지 않는다.

## 한눈에

```
 0 전제     누가 · 어떤 정책으로 · 센서가 살아 있나          (확인 못 하면 → 읽기 전용만, fail closed)
              │
 1 실행 전   tool.call ─▶ 결정적 룰 ─▶ 허용 / 사용자 승인 / 거부      (hook · 플러그인 · MCP 게이트웨이)
              │                                   │
              │                          2b 승인-실행 대조 (실행 직후)
              ▼                                   │ 다르면 → 대화 중단
 2a 결과 검사 tool.result ─▶ 룰 + 후보 ─▶ 분류기(worker, 2초 상한) ─▶ 가림 / 경보
              │
 3 사후      시퀀스 · 캠페인 · 사후 검토 · 반증 ─▶ 이후 실행 제한 (원격 차단)
 ─────────────────────────────────────────────────────────────────────────────
 4 정책 변경 룰 케이스 ─▶ 변경 검토 ─▶ 평가 묶음 ─▶ 실제 기록 재생 ─▶ 분류기 측정 ─▶ 일부 장비 ─▶ 전체
```

## 0. 전제: 판정의 근거를 믿을 수 있나

| 확인하는 것 | 어디서 | 확인 못 하면 | 문서 |
|---|---|---|---|
| 장비 신원 | 등록 토큰 → 장비 인증서(mTLS), 장비 토큰 | 정책·조치를 받지 못함 | [multi-host.md](multi-host.md) |
| 사람·에이전트 신원 | 이벤트의 `principal`, `agent.agent_id`(메인·하위 에이전트, OpenClaw 에이전트) | 사람 단위 판정이 `unknown` 기준으로 감 | [schema.md](schema.md) |
| 정책이 진짜이고 최신인가 | Ed25519 서명 검증, 정책 유효기간, 서명된 시작 시각(`effective_from`) | 낡거나 없는 정책 → 읽기 전용 툴만 허용 | [policy.md](policy.md), [fail-closed.md](fail-closed.md) |
| 센서가 살아 있나 | 데몬 응답, 플러그인 하트비트, hook 설치 상태 | hook은 캐시 정책·위험 등급으로 판정, 끊김·제거는 탐지 | [sensor.md](sensor.md) |

이 단이 무너지면 뒤의 판정은 의미가 없다. 그래서 여기서는 사용자 승인으로도 넘어갈 수 없다(CLAUDE.md "Fail closed").

## 1. 실행 전: 결정적 룰만

- **무엇을**: `tool.call` 하나. 툴 이름, 인자, 센서가 붙인 상태 label(`sga_*`: 출처, 내려받은 파일, 위임, 사람 위험도, 차단 목록).
- **누가**: Claude Code hook(PreToolUse), OpenClaw 플러그인(`before_tool_call`), MCP 게이트웨이. 판정은 모두 같은 로컬 엔진과 서명된 룰이다.
- **결과**: 허용, 사용자 승인, 거부(단일 호출 거부·대화 중단·격리). 여러 룰이 걸리면 가장 강한 것이 이긴다. 승인이 거부를 뒤집지 못한다([detection.md](detection.md) "판정 4종과 평가 순서").
- **사람에게 물을 수 없는 경로**(MCP 게이트웨이)에서 승인 판정이 나오면 거부한다.
- **시간 상한**: hook 3초. 넘으면 hook이 막는다(fail closed). 그래서 이 경로에는 분류기를 넣지 않는다.

## 2a. 결과 검사: 룰 + 분류기

- **무엇을**: `tool.result`. 툴이 가져온 내용이 모델에게 넘어가기 전이다.
- **순서**: 출처 label → 집행 룰(서명 패턴: 알려진 인젝션 문구) → 후보 룰(외부 출처 + 넓은 그물) → 걸린 것만 분류기.
- **분류기**: 데몬이 띄운 별도 프로세스(worker)에서 돈다. 데몬은 결과 하나에 최대 2초만 기다린다. 다 못 읽었으면 `unsure`다. worker가 죽거나 멈추면 그 결과는 `unavailable`이고 룰만으로 판정한다([classifier.md](classifier.md) 6, 11절).
- **결과**: `malicious` → 결과를 가린다(가림). 이후 민감·파괴 행동은 분류기만이 근거면 사용자 승인, 서명 패턴이 근거면 거부. `unsure` → 경보.
- 분류기의 판정은 label(`sga_judge_*`)일 뿐이고, 무엇을 할지는 서명된 룰이 정한다.

## 2b. 승인-실행 대조 (2026-11-17 새로)

- **빈자리**: 사용자 승인 창은 에이전트가 띄우고, 사람이 누르면 바로 실행한다. 승인과 실행 사이에 센서가 끼어들 수 없다. 보안팀 보류(실행 직전 재검사)를 없애면서 이 빈자리가 드러났다.
- **메우는 방법**: 실행 직후에 대조한다. hook이 실행 전과 후의 툴 입력 지문을 붙이고, 데몬이 비교한다. 다르면 `approval-execution-mismatch`(critical)가 걸리고 그 대화의 이후 툴 호출을 모두 막는다.
- 결과가 오지 않은 채 다음 프롬프트가 오면 "거부"로 기록한다. 예전에는 사용자의 "아니오"가 기록에 없었다.
- **한계**: 잡는 것이지 막는 것이 아니다. 승인과 다르게 실행된 한 번은 이미 일어났다. Claude Code만 해당된다([fail-closed.md](fail-closed.md) 4-1).

## 3. 사후: 상관 분석과 이후 실행 제한

| 무엇 | 어디서 | 결과 |
|---|---|---|
| 앞뒤 행동 연결(인젝션 뒤 민감 행동, 보호 데이터 조회 뒤 외부 전송, 위임 사슬) | 로컬 엔진의 시퀀스 룰, 출처 추적 | 다음 행동을 실행 전에 막음 |
| 여러 사람·장비에 걸친 같은 출처 | 관제 서버 캠페인 탐지 | 콘솔 경보, 원격 차단 |
| 사용자가 승인한 high·critical 호출 | 승인 감사 화면의 사후 검토 큐 | 확인함·문제 있음, 감사 체인 |
| 분류기가 본 것 | 콘솔 대기열(검토·집행·정상·실패) | 정상 판정도 표본으로 확인(분류기 오판 찾기) |
| 막았는데 실행된 흔적 | 막은 호출의 결과가 도착(`sga_enforcement_contradicted`) | 막았다는 기록을 반증으로 바꿈 |

여기서 내린 판단은 **이후** 실행을 제한한다(대화·사람 차단, 플러그인·스킬 격리). 이미 일어난 일을 되돌리지는 못한다.

## 4. 정책 변경: 나가기 전에 검증

```bash
uv run python scripts/verify_policy.py                                   # 1~4
uv run python scripts/verify_policy.py --db data/archive-2026-11-15.db    # + 실제 기록 재생
uv run --extra classifier python scripts/verify_policy.py --model data/models/protectai-v2
```

| 단계 | 하는 일 | 실패 기준 |
|---|---|---|
| 1 룰 로드 | 스키마, 정규식, 후보 태그 | 하나라도 안 읽히면 실패 |
| 2 룰 케이스 | `tests/rule_cases`: 모든 룰의 정탐·정상 케이스 | 하나라도 틀리면 실패 |
| 3 변경 검토 | 기준(`HEAD`) 대비 추가·삭제·비활성·응답 약화·심각도 하향·버전 그대로인 내용 변경 | 실패는 아니고 **REVIEW**: 사람이 읽는다 |
| 4 평가 묶음 | `scripts/evaluate.py`: 공격·우회·정상을 집행 지점별로 | 설계와 다르면 실패 |
| 5 실제 기록 재생 | `scripts/replay_history.py`: 관제 DB 사본으로 룰별 새로 걸림·안 걸리게 됨 | 바뀐 것이 있으면 REVIEW(`--review`로 tp/fp 판정표) |
| 6 분류기 측정 | `scripts/eval_classifier.py`: 정탐률·오탐률·지연 | 표를 읽고 판단 |

통과하면 단계적 배포로 내보낸다([policy.md](policy.md) "단계적 배포와 적용 시작 시각"): 일부 장비(`sga-server policy stage`) → 확인 → 전체(`promote`, 필요하면 서명된 시작 시각) → 문제가 있으면 `discard`. 서버에서 정책 파일을 바로 다시 읽는 것은 배포가 진행 중이면 거부된다.

룰을 튜닝하는 사람은 사용자다. 이 스크립트는 판단을 대신하지 않는다. FP/FN을 보여 주고, 약해지는 변경이 조용히 지나가지 않게 한다.

## 남은 빈자리

- **실행 전에 막을 수 없는 것**: 사용자 승인 이후의 변조(2b가 실행 직후에 잡음), hook을 지운 PC(탐지만), 결과 가림을 Claude Code가 실제로 적용했는지(미확인으로 기록).
- **데몬은 요청을 하나씩 처리한다.** 분류 중인 결과가 있으면 다른 hook이 최대 2초 기다린다. hook의 3초 제한 안이지만 여유가 크지 않다.
- **3단의 사후 판단은 이후만 제한한다.** 이미 실행된 파괴적 행동은 되돌리지 못한다.
- **4단의 평가는 우리가 만든 묶음과 공개 데이터셋 하나(InjecAgent)뿐이다.** 실제 기록 재생이 이를 보완하지만, 기록에 없는 공격은 재생으로도 보이지 않는다.
