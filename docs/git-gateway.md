# Git 게이트웨이 (2026-11-18)

2026-11-18 사용자 결정(방식 B)이다. 에이전트가 평소처럼 `git push`를 하면 **관제 서버의 Git 게이트웨이**가 작업 권한을 확인하고, 범위 밖 브랜치·경로를 거부한다.
- 통제를 hook(같은 사용자 권한이라 우회 가능)이 아니라 **자원 쪽**에 둔다(`CLAUDE.md` Zero-trust requirements).
- 내려받을 것이 없다(Git 내장 `upload-pack`·`receive-pack --stateless-rpc`).

## 경로

```
에이전트의 git ──(작업 권한: Git 자격 증명 도우미)──▶ 센서 로컬 Git 프록시(127.0.0.1)
        ──(장비 토큰·장비 인증서 추가)──▶ 관제 서버 /v1/resources/git/<프로젝트>.git
        ──▶ 온라인 재검사 · 대화별 위협 판정 · 서버가 고정한 pre-receive hook ──▶ 프로젝트 저장소
```

| 구성 요소 | 파일 | 하는 일 |
|---|---|---|
| Git 게이트웨이 | `server/resource_git.py` | Git smart HTTP. 가져오기는 `source.read`. push는 아래 순서로 판정한다 |
| push 정책 | `server/git_policy.py` | `core.hooksPath`로 서버가 고정한 pre-receive hook. 저장소 안의 hook은 쓰지 않는다 |
| 센서 프록시 | `sensor/task_git.py`, `sga-sensor run --git-proxy 127.0.0.1:PORT` | 루프백 전용. 장비 자격 증명을 붙여 전달만 한다. 판정은 서버가 한다 |
| 자격 증명 도우미 | `python -m sg_advance.sensor.task_git credential --grant-file F` | 0600 일반 파일의 작업 권한을 HTTP 비밀번호로 준다. 다른 사람이 읽을 수 있는 파일은 거부 |
| PR·CI | 자원 MCP 도구 `create_pr`(`pr.create`), `run_ci`(`ci.run`) | push된 작업 브랜치에 대해 기록·실행 |

## push 판정 순서

1. **장비 인증과 작업 권한**(`task_access.online_claims`): 사람·장비·세션 등록·정책 버전·장비 상태·위험도·원격 차단·회수를 온라인으로 확인한다. 쓰기 권한(`source.write`·`tests.write`)이 없으면 거부한다.
2. **대화별 위협 판정**(`gateway_state`): push 의도(대상 브랜치)를 그 대화의 엔진으로 판정한다. 빈도 제한·시퀀스 룰이 앞선 호출을 기억한다.
3. **실행 직전 재검사**: 1을 한 번 더 한다(그사이 회수됐으면 git을 실행하지 않는다).
4. **push 정책 hook**: 아래 규칙. 하나라도 걸리면 push 전체를 거부한다.
   - 보호 브랜치(`main`, `master`), 브랜치 삭제, 강제 push(fast-forward가 아님): 거부
   - 배포 브랜치(`deploy/*`, `release/*`, `prod*`)와 태그: `deploy.production`이 필요하다. 이 권한은 작업 권한에 넣을 수 없으므로 이번 단계에서는 모든 에이전트에게 거부한다
   - 작업 브랜치(`feature/`, `fix/`, `test/`)만 허용
   - 바뀐 파일마다 파일 게이트웨이와 같은 기준을 적용한다. `src`·`docs`는 `source.write`, `tests`는 `tests.write`이고, 숨김 파일(`.env`, `.github/` 등)과 지원하지 않는 경로는 거부한다. 경로는 작업 권한의 경로 범위 안이어야 한다
5. **기록**: ref 갱신마다 작업 권한 ID·허용 여부·이유를 이벤트와 감사 체인에 남긴다.

git 자체 설정도 서버가 강제한다(`receive.denyDeletes`, `receive.denyNonFastForwards`, `receive.fsckObjects`). 서버 쪽 git은 시스템·사용자 설정을 읽지 않는다(`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`).

**hook이 실제로 도는지 push마다 확인한다(2026-11-19).**
- 문제: Git은 실행할 수 없는 hook을 **오류 없이 건너뛰고 push를 받는다**. 실험 컨테이너에서는 Docker가 tmpfs `/tmp`를 `noexec`로 붙여 hook이 돌지 않았다. `main`은 Git의 "체크아웃된 브랜치" 규칙이 따로 막았지만 `deploy/`·`.env` push는 통과할 수 있었다.
- 수정: 서버는 push 전에 hook 파일을 직접 실행해 임의 값을 그대로 돌려주는지 확인하고, 아니면 503으로 거부한다(fail closed, 감사 기록).
- 운영: hook은 `SGA_GIT_HOOKS_DIR`(실행 가능한 디렉터리) 아래에 둔다. 실험 compose는 이 용도의 실행 가능 tmpfs를 따로 붙인다. 관제 서버 이미지는 `git`을 포함한다.

## 작업 권한

작업 권한에 넣을 수 있는 동작에 `pr.create`, `ci.run`을 추가했다(`task_grants.SUPPORTED_ACTIONS`).

| 프로필 | 동작 |
|---|---|
| `coder` | 소스 읽기·수정, 테스트 수정, PR 기록, CI 실행 |
| `tester` | 소스 읽기, 테스트 수정, CI 실행 |
| `reader` | 소스 읽기 |

역할 기본값에서 개발자는 PR 기록과 CI 실행, QA는 CI 실행만 갖는다. 발급할 때와 매 접근마다 역할 권한과 작업 권한을 모두 확인한다.

## CI

`SGA_RESOURCE_CI_COMMAND`를 설정했을 때만 돈다(비어 있으면 "CI is not configured").
- 동작: push된 브랜치를 `git archive`로 임시 폴더에 풀고, 제한 시간(`SGA_RESOURCE_CI_TIMEOUT_SECONDS`, 기본 120초) 안에서 최소 환경 변수로 실행한다.
- 결과: 종료 코드·소요 시간·출력 끝부분(비밀 마스킹)을 기록한다.
- **주의**: 에이전트가 push한 코드를 **이 서버에서 격리 없이** 실행한다. 격리된 실험 환경에서만 설정하거나, 실제 CI 러너로 바꿔야 한다.

## 대화별 판정 상태 (2026-11-18 사용자 결정)

자원 게이트웨이(파일 MCP, Git)는 호출마다 위협 엔진을 새로 만들었다. 그래서 앞선 호출을 기억해야 하는 룰은 게이트웨이에서 걸리지 않았다(시퀀스 룰, 빈도 제한, 대화 단위 중복 제거).
- 지금은 (장비, 대화)마다 엔진 하나를 정책 버전이 같은 동안 유지한다(`server/gateway_state.py`).
- 확인: 같은 대화에서 1분에 30번째 파일 쓰기나 push는 대화 중단 판정으로 거부되고, 그 파일·커밋은 실제로 반영되지 않는다. 다른 대화는 영향이 없다.
- 영향: 엔드포인트 데몬과 같은 빈도 제한이 게이트웨이에도 적용된다. 코딩 에이전트는 60초에 같은 툴 30번(`rate-limit-coding-agent-calls`, 2026-11-19 사용자 결정: 실제 Claude Code 개발 작업이 5번 기준에 걸렸다). 1분에 30번째 파일 쓰기나 push에서 그 대화는 막힌다.
- 한계: 상태는 이 서버 프로세스에만 있다. 재시작하면 잊고, 1시간 쓰지 않으면 정리하고, 정책 버전이 바뀌면 새로 시작한다. 여러 워커로 띄우면 워커마다 따로 센다.

## 확인 (2026-11-18, 실제 git 클라이언트)

`tests/test_git_gateway.py`. 성공 기준은 로그가 아니라 저장소의 ref와 파일이다.

| 사례 | 결과 |
|---|---|
| 개발자가 `feature/` 브랜치에 소스 push | 허용, 서버 저장소에 브랜치 생김 |
| `main`, `deploy/prod`, 태그 `v1.0`, 모르는 이름, 브랜치 삭제 | 모두 거부, `main`과 브랜치 목록·태그 그대로 |
| `production/`, `.env`, `.github/` 수정 push | 거부(hook 사유 표시), 브랜치는 이전 커밋 그대로 |
| 강제 push | 거부 |
| QA의 소스 수정 push / 테스트 수정 push | 거부(`source.write` 없음) / 허용 |
| push 전에 작업 권한 회수 | HTTP 403, git 실행 안 됨, 브랜치 없음. 첫 요청(ref 광고)의 거부도 작업 권한별로 기록(2026-11-19) |
| 저장소에 `exit 0` hook을 심어 둠 | 무시되고 `main` push는 여전히 거부 |
| PR 기록·CI | 개발자 허용, QA의 PR 기록 거부·CI 허용. CI는 설정 전 거부, 설정 후 실행 |
| 같은 대화의 30번째 push | 대화 중단 판정, 30번째 커밋은 반영 안 됨 |
| 센서 프록시 경유 | 에이전트는 작업 권한만 가지고 push 성공. Git 설정에 장비 토큰 없음. 공개 권한의 권한 파일은 거부 |
| hook을 정책 없이 실행 | 거부(fail closed) |
| hook이 실행되지 않는 환경(실행 권한 없음, `noexec`와 같음) | push 전 확인에서 503, `deploy/prod` 없음. 이 확인을 빼면 시험이 실패한다(그대로 통과했음) |
| 서버의 거부 결과 / CI 실패 출력 | 거부에만 `_meta`의 `sg-advance/denial` 표시. CI 출력에는 없음(엔드포인트가 외부 입력으로 검사) |

## 한계와 다음 단계

- **PR은 기록이다.** 검토·승인·병합 흐름은 아직 없다. `main` 병합은 게이트웨이 밖(사람)의 일이다.
- **작업 브랜치를 소유자에 묶지 않았다.** 같은 프로젝트의 다른 개발자 브랜치에도 fast-forward push는 된다. 브랜치 이름에 대화·사람을 묶는 것이 다음 후보다.
- **push 내용의 위협 검사는 경로 기준까지다.** 커밋 안의 비밀(키·토큰)은 아직 검사하지 않는다(비밀 스캔이 다음 후보).
- **파일 게이트웨이와의 관계**: 파일 게이트웨이의 쓰기는 저장소의 작업 트리(`main` 체크아웃)를 바로 바꾼다. 커밋이 아니다. 변경은 Git 게이트웨이로, 읽기는 파일 게이트웨이로 나누는 것을 권한다.
- **같은 사용자의 한계**: 사람과 같은 계정으로 도는 프로세스는 센서의 장비 자격 증명 파일도 읽을 수 있다. 프록시는 자격 증명을 에이전트의 설정·환경에서 빼 줄 뿐, 손이 닿지 않게 하지는 못한다. 강한 분리는 에이전트 격리(별도 계정·샌드박스)가 필요하다.
- **두 에이전트 실제 시연**: 2026-11-19 Claude Code 2.1.326과 Codex 0.167.0으로 개발자·QA·회수를 돌렸다([task-scenario.md](task-scenario.md)). Codex는 샌드박스가 `.git`을 막아 작업 사본의 `.git`만 쓰기 가능으로 두었다.
