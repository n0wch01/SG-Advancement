# 개인 인증과 프로젝트 RBAC

## 적용 범위

사용자 선택에 따라 기존 웹 콘솔의 Bearer 로그인을 재사용하고 개인 API 토큰을 추가했다.
서버는 사용자·토큰 만료/폐기·현재 팀 구성원·역할·프로젝트 상태를 매 요청에서 조회한다.
토큰 원문은 발급 응답에서 한 번만 보여주고 DB에는 SHA-256만 저장한다. 기본 수명은 8시간,
최대 30일이다. 사용자 중지·토큰 폐기는 다음 인증 요청부터 적용된다. OIDC·MFA는 아직 구현하지 않았다.

기존 `SGA_ADMIN_TOKEN`은 초기 설정용 `bootstrap:admin`, `SGA_DASHBOARD_TOKEN`은 공용 읽기 전용
`legacy:viewer`로 호환한다. 설정한 공용 토큰의 전체 조회 권한은 유지되므로 개인 계정과 같은 수준의
행위자 식별로 설명하면 안 된다. 개인 계정을 만든 뒤 운영에서 공용 토큰을 배포하지 않는 절차가 필요하다.
`by` 요청 필드는 기존 CLI 호환을 위해 받지만 저장하는 행위자는 인증 주체에서 가져온다.

## 역할과 범위

사용자, 팀, 팀 구성원, 역할의 권한 목록, 프로젝트별 역할 배정은 각각 별도 테이블이다.
기존 정책 배포용 `Group`은 그대로 두며 조직 팀이나 사용자 권한의 근거로 쓰지 않는다.

| 기본 역할 | 관제 권한 | 자원 권한 어휘 |
|---|---|---|
| 계정 관리자 | 계정·팀·역할·장치 사용자 연결 | 기본 없음 |
| 보안 정책 관리자 | 정책 관리, 전체 조사·감사, 승인 사후 검토 | 기본 없음 |
| 관제 담당자 | 배정 범위 조사·장치 조회·세션 차단/해제 | 기본 없음 |
| 개발자 | 배정 프로젝트의 활동·탐지 조회, 세션 등록 | 소스 읽기/수정, 테스트 수정, 개발 CI·PR |
| QA | 배정 프로젝트의 활동·탐지 조회, 세션 등록 | 소스 읽기, 테스트 수정, 테스트 CI |

자원 권한은 관제 API 권한과 별도로 평가한다. 권한 어휘가 존재하는 것과 실행 기능을 구현한 것은
다르다. 작업 권한·보호 자원 게이트웨이는 후속 구현 중이며 CI·PR·배포 연동의 완료를 뜻하지 않는다.
보안·계정 관리가 저장소 수정이나 운영 배포를 자동으로 허용하지 않는다.
역할의 권한 목록은 계정 관리자가 편집할 수 있다. 알려지지 않은 권한은 거부한다.

정책·계정·전체 감사는 시스템 범위이고, 자원 권한은 명시적인 프로젝트가 필요하다.
관제 역할은 프로젝트별로 배정할 수 있으며, 이때 등록된 해당 프로젝트 세션의 차단/해제만 지원한다.
사용자 전체 차단과 실행 중단은 다른 프로젝트 작업까지 영향을 줄 수 있어 시스템 범위가 필요하다.
환경은 프로젝트의 허용 환경 안에서 배정한다. 기본 프로젝트 환경은 개발·테스트다.

## 수집 기록의 프로젝트

1. 계정 관리자가 센서 장치를 실제 사용자 계정에 연결한다. 과거의 문자열 `owner`와 구분한
   `owner_user_id`를 사용한다.
2. 배정받은 사용자가 장치·코딩 에이전트 종류·네이티브 세션 ID를 프로젝트에 등록한다.
   관리자가 대신 등록해도 대상 사용자의 소유 장치·현재 프로젝트 권한을 확인한다.
3. 이후 수집하는 이벤트·로컬 탐지에 서버가 프로젝트와 사용자 열을 저장한다. 수집 문서의 사용자명,
   그룹·프로젝트 라벨은 권한 근거가 아니며 예약 라벨은 서버가 덮어쓴다.
4. 같은 장치/에이전트/세션의 프로젝트 등록은 변경하지 않는다. 다른 프로젝트에는 새 세션을 등록한다.
   장치 사용자가 바뀌면 기존 세션 등록을 폐기한다.

과거 기록과 미등록 세션은 `project_id=NULL`, `actor_id=NULL`로 남겨 일반 프로젝트 사용자에게
공개하지 않는다. 나중에 등록해도 예전 기록을 자동으로 재분류하지 않는다.
세션 등록은 허용된 수집 범위를 정하는 절차이며, 프로세스/사용자의 하드웨어 증명이나 파일 접근 권한
자체를 증명하지 않는다. 보호 자원의 실행 권한은 별도로 확인해야 한다.

## API와 콘솔

`/v1/admin/rbac`의 계정 관리 API와 콘솔의 **접근 관리**에서 사용자·팀·역할 배정·개인 토큰·장치
사용자를 관리한다. 일반 사용자는 배정 프로젝트와 등록 세션을 확인하고 자신의 소유 장치를 등록한다.
메뉴·변경 버튼은 서버가 반환한 권한으로 표시하며, 서버가 다시 권한과 대상 범위를 확인한다.
콘솔은 30초마다 또는 창으로 돌아올 때 권한 정보를 갱신한다. 이전에 이미 열람한 자료를 소급해서
회수하는 기능은 아니다. 폐기된 토큰의 다음 API 요청이 401이면 로그인 화면으로 돌아간다.

기존 관제 API는 명시적 권한 목록에 등록한 경로만 개인 토큰에 허용한다. 프로젝트 조회에는 요청별
SQLAlchemy ORM 조건을 적용해 목록·집계·증거·대화·위험도·승인 통계·캠페인 연관 조회를 함께 제한한다.
허용되지 않은 탐지 ID는 404로 응답한다. 범위를 알 수 없는 과거 기록, 전역 캠페인 집계는 개인의
프로젝트 조회에서 제외한다. 부분 캠페인 집계는 별도 구현이 필요하다.
새로운 원시 SQL/Core 조회를 추가할 때 이 조건을 우회하면 안 된다. 프로젝트 조회 세션의 비 ORM
SELECT는 거부하며, 새 API는 권한과 범위 회귀를 추가한 뒤 허용 목록에 등록한다.

## 확인

- 마이그레이션 `0012`: 기존 장치·이벤트·탐지·감사 행 보존, 미확인 범위 NULL, 외래키 검사 통과.
- 서로 다른 프로젝트와 미등록 기록을 섞은 조회·집계·간접 증거·타임라인·위험도·승인 통계 회귀.
- 토큰 만료·폐기·사용자 중지, 팀 역할 회수, 범위 밖 대응 거부, `by`/사용자/그룹/프로젝트 위조 회귀.
- RBAC 포함 전체 Python **981개**, 대시보드 기존 회귀 **44개**, TypeScript/배포 빌드 통과.

요청별 ORM 조건은 [SQLAlchemy의 접근 제한 방식](https://docs.sqlalchemy.org/en/20/orm/queryguide/api.html#sqlalchemy.orm.with_loader_criteria)을
이용한다. 실제 테넌트 경계의 검증 근거는 위 API 회귀이며 화면의 메뉴 숨김이 아니다.

## 브라우저 확인 (2026-11-18)

일회용 로컬 관제 서버(127.0.0.1, 임시 DB)에서 확인했다. 시험용 개인 토큰만 썼고, 끝난 뒤 서버와 토큰을 지웠다.
- 구성: 프로젝트 Alpha·Beta, 역할별 사용자 6명(개발자 Alpha·Beta, QA·관제 Alpha, 보안·신원 전역)
- 기록: 장비 2대가 실제 센서 경로로 보낸 Finding 6건

| 사용자 | 콘솔에서 보인 것 | API 확인 |
|---|---|---|
| 개발자(Alpha) | 개요·탐지·타임라인·승인 감사·접근 관리. Alpha의 Finding 3건, 자기 장치·세션, 작업 권한 발급 | Finding은 Alpha만, 정책·장비·계정 관리 403 |
| QA(Alpha) | (API만 확인) | Alpha만, 정책·장비 403 |
| 개발자(Beta) | (API만 확인) | Beta만 |
| 관제(Alpha) | 위 메뉴에 인벤토리·대응 추가, Alpha 3건·장치 1대 | Alpha 세션 차단 201(행위자는 요청의 `by`가 아니라 인증된 `soc`), Beta 세션 차단 404 |
| 보안(전역) | (API만 확인) | Finding 6건 전부, 정책 조회 허용, 계정 관리 403 |
| 신원 관리자 | 사용자·팀·역할 배정·회수·토큰 발급·폐기·계정 중지·역할 권한 편집 | Finding 403, 계정 관리 허용 |

- 콘솔에서 개발자 토큰을 폐기하자, 그 토큰의 다음 API 요청은 401이었다. 다른 사용자(QA)는 그대로 200이었다.
- 콘솔 오류는 없었다.
- 화면의 메뉴 숨김은 편의일 뿐이다. 범위의 근거는 위 API 결과다.
- 관찰: 전역 역할(신원 관리자)도 배정 내역에 실행 환경 `development`가 함께 표시된다. 동작에는 영향이 없다.
